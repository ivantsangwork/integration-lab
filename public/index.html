Integration testing ground

A bench for the problems two live systems keep running into.

I run two production systems that look unrelated and turn out to be the same shape of problem: pull from many heterogeneous sources on different cadences, normalise them into one model, score, and alert. This site is where I isolate each part of that and test it on its own, before it goes anywhere near either system.

Each bench below states what it is trying to find out, the failure it exists because of, and what the testing actually showed. Several of them run live in the browser against real endpoints.

What feeds the bench

Two production systems, one architecture

Both ingest from sources that disagree about everything — schema, units, identifiers, cadence, availability — and both have to keep producing a usable ranked view when one source misbehaves.

Why the pairing is useful. They stress the same pipeline from opposite ends. CryptoFundingWatch is numerically fussy but structurally uniform — five sources, same shape, same clock. LatticePulse is structurally chaotic — a Reddit comment and an SEC Form 4 filing have nothing in common except that both are evidence about a ticker at a point in time. A technique that survives both is probably sound.
The shape of the problem

Both systems reduce to the same five stages

The benches map onto the stages. Where each one sits is where its failures show up.

Findings so far

Notes

  • Partial availability beats a spinner. When one of five exchanges stops responding, blanking the whole view is worse than showing four live rows and one stale-flagged with its last-good timestamp. Users can reason about a known-stale number; they can't reason about an absence.
  • Normalise at the boundary or not at all. Every unit conversion that leaks past the adapter — an hourly rate that reaches the scorer un-annualised — becomes a bug that only shows up on the one venue that does it differently.
  • Ragged cadence is harder than slow cadence. LatticePulse polls social every few minutes and filings every 15–30. Comparing velocity across sources that sample at different rates needs the baseline to be per-source, not global.
  • A timeout is not a failure. The retry bench exists because of this one — after a timeout you don't know whether the write landed, and the only safe answer is an idempotency key. Bench 03 demonstrates it.
  • Deterministic scoring is a feature. Both systems use fixed formulas rather than models. It means a score can be explained, reproduced, and argued with — which matters more than accuracy when someone asks why a ticker moved up the list.

What this is. A personal testing ground, not a product and not a portfolio. The benches exist to answer specific questions about integration behaviour; several run live in the browser against real endpoints, and where a demo is simulated the page says so. Findings here inform CryptoFundingWatch and LatticePulse, which are the systems that keep raising the questions.
